## Objective

Determine whether Grok Build can use models available to the user's existing Cursor subscription by reading the signed-in Cursor Desktop session already stored on the machine. The target experience requires no browser OAuth and no manually copied API key. If feasible, credentials must be used only for Cursor inference requests and remain out of configuration files, logs, diagnostics, and persistent Grok state.

The intended result is a selectable Cursor-backed model using the user's existing Cursor Desktop session, with Grok Build retaining control of its own tools and permissions. Use the pinned `pi-cursor` implementation as the compatibility reference. This is not a claim that Cursor exposes a conventional, system-role-preserving inference API: as in Pi, caller instructions are represented in a user-role `<rules>` message and Cursor's own agent system prompt remains in force. Do not execute Cursor-native tools on the user's behalf.

## Review disposition

A GPT-5.6 Sol subagent reviewed the initial plan after it was written. The user clarified that `pi-cursor` already provides the desired user-facing model-provider experience, so the implementation target is revised to match that working adapter rather than require OpenAI-style system-role semantics. That reference converts caller system instructions to a user-role `<rules>` message, exposes Grok/Pi tools through Cursor's MCP stream, pauses the response for host-side tool execution, and sends results back on the same stream. Grok must preserve its own permission decisions while implementing the equivalent lifecycle. This revision removes system-role preservation as a feasibility gate; the prompt-priority difference remains a documented compatibility limitation.

## Feasibility findings — 2026-09-14

The pinned reference confirms a model-provider integration over Cursor's `AgentService.Run` stream. Its prompt builder records that the server discards system-role entries, so Pi places caller instructions in a user-role `<rules>` message ([`root-prompt.ts`](https://github.com/Rahularya01/pi-cursor/blob/324d2061cac068110b2ac9c783ef419b1fdf0501/src/stream/root-prompt.ts#L13-L17), [`request-build.ts`](https://github.com/Rahularya01/pi-cursor/blob/324d2061cac068110b2ac9c783ef419b1fdf0501/src/stream/request-build.ts#L635-L646)). Its protocol inventory identifies `Run`/`RunSSE` as conversational paths and both required model-catalog calls ([`AgentService` inventory](https://github.com/Rahularya01/pi-cursor/blob/324d2061cac068110b2ac9c783ef419b1fdf0501/src/proto/agent_pb.ts#L14362-L14414), [`protocol.md`](https://github.com/Rahularya01/pi-cursor/blob/324d2061cac068110b2ac9c783ef419b1fdf0501/docs/protocol.md#L26-L31)). This is sufficient architectural evidence to proceed with a Pi-compatible provider; it does not establish a stable public API or conventional system-role behavior.

A disposable local-session probe attempted model discovery. Its catalog calls returned no decodable models, but diagnostics were suppressed and it exited before the after-snapshot, so the result cannot distinguish authentication, transport, status, or decoding failure. `bun --check` unexpectedly executed the probe twice (once by the implementation agent and once by a reviewer); both runs read only `cursorAuth/accessToken` through SQLite `readOnly: true`, made the two catalog calls, and exited before `AgentService.Run`. The token was not printed, no refresh-token path was invoked, and no inference or Cursor-native tool action occurred. This is inconclusive and is not acceptance evidence; the secure, instrumented smoke test remains required.

**Disposition:** Proceed with a native Cursor-backed model provider that matches Pi's integration semantics. Treat the user-role `<rules>` prompt mapping and private-protocol dependence as explicit limitations. Keep Cursor-native tool execution disabled; Grok-advertised tools must pass through Grok's permission-controlled host and resume on the same Cursor stream.

## Scope

Implementation scope:

- Discover the current Cursor Desktop access token from its local application state database, initially following the `cursorAuth/accessToken` lookup used by CodexBar and `pi-cursor`.
- Discover the models and parameter variants available to that account using all required model-catalog RPCs.
- Send and stream model requests through Cursor's current Connect/protobuf HTTP/2 protocol, translating them into Grok Build's sampling and tool lifecycle.
- Make Cursor selectable as an inference provider, with clear local-session status and actionable authentication failures.
- Add offline protocol, credential, lifecycle, and security tests plus an explicitly invoked live smoke path; document tested platform coverage and the unsupported/private-protocol boundary.

Not included in the first release:

- Browser-based Cursor OAuth, refresh-token exchange, or a separate Cursor credential store.
- Cursor usage/allowance dashboards. A valid usage-summary session does not establish inference API compatibility or metering behavior.
- Cursor-native shell, filesystem, fetch, web, computer-use, or other agent tools. All tool execution and approval must remain under Grok Build's existing authority and sandbox.
- Arbitrary Cursor-compatible endpoints or third-party services receiving the Cursor session token.

## Evidence and architecture

Grok Build's configurable API backends currently cover OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages ([backend type](../../crates/codegen/xai-grok-sampling-types/src/types.rs), [request dispatch](../../crates/codegen/xai-grok-sampler/src/actor/request_task.rs), [custom model guide](../../crates/codegen/xai-grok-pager/docs/user-guide/11-custom-models.md)). Its named auth-provider hook supplies bearer tokens but does not add a transport or protocol ([auth-provider implementation](../../crates/codegen/xai-grok-login/src/auth_provider.rs)). Cursor therefore needs a dedicated backend and credential source; configuring `api_key` or a token helper against a Cursor URL is insufficient.

The reference provider at [`Rahularya01/pi-cursor`](https://github.com/Rahularya01/pi-cursor/tree/324d2061cac068110b2ac9c783ef419b1fdf0501) implements local credential resolution (`src/auth/cli-credentials.ts`), two model-discovery calls (`src/stream/model-discovery.ts`), unary HTTP/2 requests (`src/client/h2-unary.ts`), bidirectional streaming (`src/client/h2-session.ts`), Connect framing (`src/client/bridge.ts`), conversation/blob/checkpoint handling (`src/stream/request-build.ts`, `src/stream/server-messages.ts`), and Cursor's reconstructed schema (`proto/agent.proto`). Its request path is based on reverse-engineered Cursor interfaces and is not a documented or stable public inference API.

Grok Build already has `prost`, `rusqlite`, `reqwest` with HTTP/2, Tokio, and shared SQLite support in the workspace. That does not prove the existing HTTP client can satisfy Cursor's bidirectional Connect stream. Also, do not reuse [`xai-sqlite-journal`](../../crates/codegen/xai-sqlite-journal/src/lib.rs)'s `JournalMode::open_readonly` for Cursor's database without proving it is non-mutating: its network-filesystem branch opens read/write and converts journal mode.

## Work plan

### Phase 0 — Compatibility contract and staged validation

Implementation is authorized and may proceed in isolated production-code slices while feasibility is validated. This phase no longer blocks credential-source, transport, or sampler work. During development the provider is enabled only from the app's Settings → Models screen; a `[model_providers.*]` or `[model.*]` backend entry does not turn on account discovery. The provider remains experimental until Phases 1–3 pass their acceptance criteria and a supported account path has been validated. Source builds use `~/.grok-build` by default so their app settings, sessions, and caches do not collide with an installed Grok profile; explicit `GROK_HOME` remains an intentional override. Use the currently signed-in Cursor Desktop session only for an explicitly invoked live check; never print or persist its token.

1. Establish a bearer-token destination policy before any catalog or inference request. Use a finite trusted-origin allowlist or validated Cursor-owned regional discovery; never trust arbitrary model config, environment URL, redirect, or user-edited Cursor config as an authorization destination. Retain TLS verification, cancellation, and secret redaction.
2. Confirm the active Cursor Desktop database path and whether the current `accessToken` is readable while Cursor is running, including WAL-backed state. Prove the main database and WAL are unchanged; do not create the database, change journal mode, or checkpoint. SQLite may create or update `-shm` for WAL locking/index coordination; record that runtime behavior explicitly and keep application code from writing other sidecars. The first disposable probe was inconclusive, so this evidence still needs to be gathered with a secure instrumented harness.
3. Call both `AgentService/GetUsableModels` and `AiService/AvailableModels`. Reconcile the usable model list with parameterized metadata; identify which fields are server-provided and which context/output values would have to be inferred. The reference notes that the Run request has no max-output field, so such a value can only be local budgeting metadata, not an upstream guarantee.
4. Use the working `AgentService/Run` integration demonstrated by `pi-cursor`; do not require a separate inference-only RPC. Follow its prompt mapping, which wraps caller instructions in a user-role `<rules>` message because Cursor's server discards system-role entries. This is an accepted compatibility limitation, not a claim of system-role equivalence.
5. Exercise the bidirectional tool lifecycle over two Grok sampler calls sharing one retained Cursor stream. Cursor's MCP request ends the first host response; Grok then applies its existing permission/tool path, and the next sampler call sends the matching MCP result on the parked bridge before streaming the continuation. Encode permission denials as protocol-valid MCP error results (`success.isError=true`, matching the pinned Pi behavior), not as an unverified wire-level denial variant. Correlate primarily by `x_grok_session_id`, with provider/model identity and a bridge generation; correlate each pending result by Cursor exec ID and MCP tool-call ID. Reject a request without a stable session ID rather than attach a result to an ambiguous bridge.
6. Inject every known Cursor-native exec and interaction-query class, including shell/file/fetch/web paths. Return a protocol-valid rejection for known variants where the schema defines one; an unknown side-effect-capable variant must terminate the stream safely rather than inventing a reply, ignoring it, or auto-approving it.
7. Exercise KV blob get/set, checkpoint updates, multi-turn prompt history, missing-blob behavior, cancellation while parked, and transport loss. Establish memory/frame bounds and recovery semantics.
8. After destination validation and the local credential source are in place, make one minimal, low-output live inference request through `AgentService/Run`. Record sanitized status, timing, and event shapes. Any observation of dashboard usage/allowance is optional and non-gating; Grok does not implement a usage dashboard.

**Release gate:** Keep Cursor behind the app's explicit opt-in setting and identify it as experimental while work is in progress. Do not include it in a general release or describe it as release-ready until the local-session credential source, merged model discovery, text streaming, same-stream tool continuation through Grok's normal permission path, and safe rejection/termination of Cursor-native side-effect requests have passed their implementation acceptance tests. Then validate one supported account path. A system-role-preserving API is not required. If account/model access or safe tool continuation cannot be made to work, report the specific integration blocker before enabling general availability.

### Phase 1 — Local Cursor Desktop credential source

1. Add a small credential-source abstraction in the auth/config boundary. Invoke it only when the user selects the Cursor provider; it must not become a global credential fallback.
2. Read only the access-token value from Cursor's `state.vscdb` `ItemTable` entry `cursorAuth/accessToken`. Start with the macOS path on this machine; include Linux/Windows paths only to the extent Grok Build supports and tests them.
3. Open the database with `SQLITE_OPEN_READ_ONLY`, which cannot create the database, change journal mode, or checkpoint WAL. SQLite may create or update its `-shm` file as required for WAL locking/index coordination; this is a documented runtime side effect, not a credential or database-content write. Verify the main database and WAL remain unchanged with an active WAL fixture and a separate writer connection held open. A write occurring concurrently with the credential lookup is not yet covered by the fixture. Do not read or exchange `cursorAuth/refreshToken`; an expired token means Cursor Desktop needs to refresh its own session.
4. Check token expiry locally before use. Keep the credential in memory only, minimize copies at provider boundaries, and exclude it from `Debug`, tracing, errors, crash reports, model caches, and serialized sampler/session state.
5. Fail with a non-secret message when Cursor is absent, signed out, unreadable, or expired. Do not fall back to Grok's account token or an unrelated provider key.

**Acceptance:** Fixture tests cover valid, expired, malformed, missing, corrupt, locked, WAL-backed, missing-SHM, and platform-path cases; filesystem assertions prove no main-DB/WAL mutation or DB creation, and record whether SQLite creates its `-shm` coordination file. No application code writes other sidecars. Tests verify redacted `Debug` output and access-token-only lookup. A runtime log/disk scan and platform CI remain release checks. No refresh token or access token is copied into Grok-owned persistent state or logs.

## Definition of done

- The provider follows the working Pi integration shape: caller instructions are sent in a user-role `<rules>` message, Cursor's own agent system prompt remains active, and this precedence limitation is documented.
- A user signed into Cursor Desktop can select an account-available model and stream inference without Cursor browser authentication or a manually copied API key. Any separate Grok account login remains governed by Grok Build's existing app-auth behavior.
- Grok-advertised tools pass through Grok's normal permission gate and their results resume the same Cursor stream; Cursor-native tools are not executed.
- Same-stream tool continuation, permission denial, cancellation, retries, checkpoint/history, and KV/blob behavior are correct and bounded.
- Cursor's access token is sourced read-only, kept in memory only, never logged or persisted, and sent only to vetted Cursor inference origins.
- Model discovery, protocol mapping, session failures, supported platform paths, and unsupported capabilities have automated coverage and user documentation.
- Live acceptance confirms this account works without exposing or persisting its credential. Usage and allowance reporting remain outside this feature.

## Pi-compatible behavior and limits

- Caller system instructions are wrapped in a user-role `<rules>` message because Cursor discards system-role entries on this path. Cursor's own agent instructions remain active; do not claim equal priority to a conventional system message.
- Cursor model tools are exposed as MCP. Grok receives only calls for the tools it advertised, runs them through its existing permission/execution path, and sends one matching MCP result on the same parked Cursor stream from the next sampler call. Permission denials use the MCP error-result encoding shown by the pinned Pi implementation (`success.isError=true`). Cursor-native shell/filesystem/web/computer-use tools and hosted web approvals are rejected; Pi's local executors and auto-approvals are not copied.
- `temperature` is unsupported by the reference path; tool choice is limited to `auto` and `none`. The Run request has no output-token cap, so `max_completion_tokens` can only budget locally. Document any initial Grok configuration that cannot express the supported choices.
- Context/output metadata is partly inferred. Usage/cache/cost metadata is approximate. Image and tool-result size/format limits must be carried over or conservatively tightened.
- The protocol is private and reverse engineered. The adapter follows a pinned schema/reference commit and must fail closed on unknown side-effect-capable variants.

## Main risks and decisions

- **System-prompt mapping:** The AgentService server discards system-role messages. Like `pi-cursor`, the adapter will put caller instructions in a user-role `<rules>` message; Cursor's system instructions retain their higher authority. Document this behavior and do not claim ordinary system-role semantics.
- **Bidirectional tool lifecycle:** Cursor pauses its stream for MCP replies, while Grok's current flow executes returned tool calls after sampling completes. Match Pi's two-sampler-call pattern: return the pending tools from the first call, retain the Cursor bridge, and send their results from the next call. Use `x_grok_session_id` plus provider/model identity and a bridge generation; `ConversationGroupId` alone can span child sessions. Add the smallest session-level request/reply path needed to bridge that gap.
- **Native side effects:** Cursor's protocol includes native shell, file, fetch, web, and other interactions. All known variants need explicit fail-closed replies; unknown variants must terminate safely.
- **Private protocol drift:** Cursor can change protobuf fields, headers, host routing, model names, or authentication behavior. Pin schema provenance, test unknown fields, and keep a clear failure diagnostic; do not claim provider stability.
- **Live SQLite safety:** The auth database is actively owned by Cursor and may use WAL. Read-only behavior must be demonstrated; never alter or checkpoint the database from Grok Build.
- **Entitlement/metering uncertainty:** Successful calls do not prove which subscription pool is charged, quota guarantees, or long-term eligibility. Usage/allowance observation is optional and external to this feature; do not imply guarantees.
- **Model metadata limits:** `GetUsableModels` alone lacks context/output limits and parameter variants. Merge the second catalog RPC, mark inferred values, and do not represent local output budgets as upstream request limits.
- **Host routing:** Cursor can resolve a regional agent URL from its CLI configuration. Accept only vetted Cursor origins; do not trust arbitrary configured destinations with a bearer token.
- **Platform scope:** The reference resolves macOS Keychain/IDE DB, Linux, Windows, and WSL sources. The first Grok Build release should support only paths covered by tests; defer the remaining paths explicitly.
- **Reference reuse:** Port only the protocol behavior needed for Grok Build. Keep upstream commit and license provenance with any derived schema or code; do not import Cursor-native tool execution or browser OAuth.

## Implementation order and dependencies

The secure credential source and transport/model-catalog slices can be implemented first behind isolated interfaces and fake fixtures. Keep provider selection behind the app's explicit experimental opt-in; do not move beyond that to general release until model discovery, same-stream tool continuation, native-message rejection, and secret-routing acceptance tests pass.
